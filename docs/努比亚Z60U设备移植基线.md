## 文档定位

## 已确认的硬件事实

- 产品型号：NX721J，启动设备代号 PQ83A01。
- SoC 平台：实时设备树为 Qualcomm Pineapple；实机 qcom,msm-id 与 UEFI giulia.dts 完全一致，当前按 SM8650/Lanai 家族和 SOC_TYPE=2 适配。
- 内存和保留区：已从实时设备树和 UEFI giulia 内存库完成交叉比对，关键 UEFI、Kernel、Display 和 TZApps 区域一致。
- 存储：UFS 控制器基址 0x1d84000，PHY 为 Pineapple UFS PHY；这是后续 NativeUfs 的实机入口。
- 显示：DSI 面板 BF068_RM692H0，实测活动模式为 1116x2480，支持 60、90、120 Hz 命令模式。
- 触控：Goodix Berlin，节点兼容字符串 goodix,brl-d，挂在 QUPv3 GENI SE1 的 SPI 控制器上。
- GPU：Adreno Gen7.9.1，KGSL 节点基址 0x3d00000，芯片标识字节为 43 05 14 01，GMU 和 SMMU 节点均存在。

这些值来自 TWRP 下的实时设备树、sysfs 和分区只读采集。原始转储不进入 Git。

## 与 sheng 的边界

UniXNU-sheng 的 GPU 已经成功驱动，这是重要的代码和验证参考，但它的板级硬件是 SM8550/A740，不能直接复用以下内容：

- SM8550 的 KGSL、GMU、SMMU、时钟、电源和固件地址。
- sheng 的 NativeNovatekTouch 和 NT36532E 触控协议。
- sheng 的显示 DPU、面板和 framebuffer 参数。
- sheng 的 UEFI 包、DT 地址、CPU 频率表和 PMIC 寄存器。
- 任何以 sheng- 命名且在实现中写死地址的板级驱动。

可以复用的主要是结构、构建顺序、日志方法、GPU 驱动的抽象边界、DarwinBoot 载荷组织方式，以及已经验证过的 XNU/Metal 接口修补思路。Z60U GPU 适配应以 Pineapple 实时 DT 和 Linux KGSL 状态为输入，不能以 sheng 数值猜测。

## 当前仓库状态

- 分支：codex/nx721j-scaffold
- 来源：UniXNU-sheng 的完整本地副本，保留子模块边界。
- 当前没有把 sheng 的 board.toml、defconfig、触控驱动和 GPU 常量宣称为 Z60U 配置。
- 当前没有提交任何 Apple 原始文件、设备序列号或手机转储。
- ios-sweet 仍作为旧的 SM7150/XNU 研究工作区；本仓库用于正式的 UniXNU Z60U 设备结构。

### 当前新增的目标边界

- `scripts/make-nx721j-adt.py` 是独立的 NX721J ADT 生成器。它使用实时 Pineapple DTB 已确认的根兼容字符串、8 个 CPU MPIDR、PSCI `smc`、GIC、19.2 MHz 计时器、UFS 主控和 Pineapple UFS PHY；不使用 sheng 的根身份或 SM8550 UFS 兼容字符串。
- `scripts/build-nx721j-payload.py` 只负责把调用者明确提供的 ARM64 Mach-O、NX721J ADT、可选 trust cache/Data seed 组织成官方 UniXNU payload FAT；UniXNU.efi 和 DarwinBoot.efi 仍由 UEFI 固件提供。
- `scripts/check-nx721j-ufs-facts.py` 只读校验外部 `/proc/device-tree` 快照，防止后续 UFS 驱动把另一块 Qualcomm 板子的时钟、reset、SMMU 或 DMA 参数带入 NX721J。
- NX721J 实时内存是 2 GiB + 6 GiB + 8 GiB 三段物理 DDR。ADT 的 `dram-base`/`dram-size` 是 XNU 使用的单一连续窗口，必须显式传入，不能把 16 GiB 直接当作从 `0x80000000` 开始的连续空间。
- 当前 `drivers/NativeUfs` 的主动传输仍是 sheng/SM8550 实现，包含 sheng GCC、SMMU、兼容字符串和 `sheng-*` 持久化策略；NX721J 只增加了显式门控的被动 profile，不能因为 ADT 出现 `qcom,ufshc` 就直接进入 sheng 主动路径。

### 当前 NativeUfs 目标边界

当前运行阶段退回到 XNU first-entry 验证：`nx721j_probe_defconfig` 关闭
`CONFIG_XNU_NATIVE_UFS`，`board.toml` 不构建 `NativeUfs` archive，payload
不带 `native-ufs-*` 或 root 参数。此前的被动 UFS 分支保留为未启用的
实验代码，不作为本阶段内核的一部分。

payload 工作流会复制 kernel artifact，再仅对副本运行入口/MMU 标记；原
kernel artifact 不被修改。蓝色标记表示 XNU 入口代码已执行，品红标记
表示执行到打开 MMU 之前，若跨过 MMU 指令则在 6 秒后请求 PSCI system
reset。此探针不带 sheng UEFI 字体，也不加载存储驱动。

以下关于 UFS 被动探测的记录是上一阶段实现边界，不代表当前 first-entry
镜像会加载 NativeUfs：

公共 `NativeUfs` 子模块已增加 `Nx721jUfs.h` 和显式目标门控：

- `native-ufs-target=nx721j native-ufs-probe=2` 只读取 NX721J UFSHCI 标准寄存器和 Apps SMMU ID 寄存器，并打印已验证的 host/PHY/GCC/SMMU 窗口、SID `0x60`、reset `0x19`、DMA 池和时钟数量。
- NX721J 不会进入现有 sheng 的 GCC 偏移、队列接管、SMMU 重配置、PHY/复位操作或根卷发布路径。
- UFSHCI 队列、UPIU/SCSI、缓存屏障、GPT/根卷解析仍是官方 UniXNU 的通用候选代码；Ace5 的 Giulia SMMU 重绑定、SM8650 GCC 偏移和固定分区窗口不属于 NX721J。
- `scripts/build-nx721j-payload.py` 现在强制执行同一边界：只接受显式的 `native-ufs-target=nx721j`，UFS 探测当前只能是 `native-ufs-probe=2`，任何 `native-ufs-root=` 都会在主机打包阶段被拒绝。这样不会把尚未验证的 sheng/SM8550 主动传输路径放进临时镜像。
- `configs/nx721j_probe_defconfig` 只打开通用 ARM DT、CPU、架构计时器、启动进度和 NativeUfs 入口，明确关闭 LegacyDisplay、MobileDisplay、Adreno 和 ARM virtual 平台；它目前没有接入仍为 sheng 脚手架的 `board.toml`。

这一步是源代码边界和被动探测阶段，不等于 NX721J 已经能够读盘。必须先在 macOS/XNU 工具链实际编译，再用 `fastboot boot` 启动带上述只读参数的 payload，确认 UFSHCI/SMMU 实测状态后，才能决定是否实现 Pineapple 的时钟、PHY、DMA 和 SMMU 接管。

### NX721J UFS 依赖证据

实时 `/proc/device-tree` 与 UEFI `Resources/DTBs/giulia.dts` 对 UFS 主控给出同一组硬件事实：

- `ufshc@1d84000` 的兼容字符串是 `qcom,ufshc`，五段寄存器窗口是 `0x1d84000/0x3000`、`0x1d88000/0x8000`、`0x1d90000/0x9000`、`0x1da5000/0x2000`、`0x1da4000/0x10`，中断是 GIC SPI `0x109`。
- `ufsphy_mem@1d80000` 的兼容字符串是 `qcom,ufs-phy-qmp-v4-pineapple`，两条 lane，UFS 主控通过 `phys`/`phy-names` 连接到它。
- UFS 主控需要 9 个时钟：`core_clk`、`bus_aggr_clk`、`iface_clk`、`core_clk_unipro`、`core_clk_ice`、`ref_clk`、`tx_lane0_sync_clk`、`rx_lane0_sync_clk`、`rx_lane1_sync_clk`。前 5 个及 3 个 lane 同步时钟来自 Pineapple GCC `clock-controller@100000`，`ref_clk` 来自 RPMh clock controller。
- DT 还明确给出 GCC reset ID `0x19`、PHY、`gcc_ufs_mem_phy_gdsc`/`gcc_ufs_phy_gdsc` 电源依赖、RPMh regulator supplies、两条 interconnect（`ufs-ddr`、`cpu-ufs`）以及 Apps SMMU stream `0x60`；`qcom,iommu-dma = "fastmap"`，DMA 地址池为 `0x1000..0xffffffff`。
- 这些字段是 NX721J 原厂硬件依赖，不是 Ace5 二进制。官方 UniXNU 的 UFS 命令队列、SCSI、GPT/根卷解析可以作为通用代码参考，但 `NativeUfs` 当前的 SM8550 GCC 检查、`qcom,sm8550-ufshc` 匹配和 `sheng-*` 数据策略必须隔离，不能直接拿来作为 NX721J 驱动。

## 移植阶段

### 第一阶段：UEFI 和启动载荷

先在独立 uefi-z60u 中完成 Lanai/SM8650 基线编译。使用 Binaries/giulia 的 SM8650 资源，SimpleFb 优先，不立即引入 Z60U 专用 DSI XML。验证目标是 UEFI 菜单、GOP、USB、UFS 枚举和 DarwinBoot 载荷入口。

### 第二阶段：XNU 最小启动

建立 nx721j 的 board 配置和 ADT 生成器，先只启用单核、PSCI、GIC、定时器、内存图和 framebuffer。首个 XNU 目标是能输出启动进度并停在可诊断状态，不同时启用触控、GPU 或写入 userdata。

### 第三阶段：只读 UFS 和系统根

依据实机 UFS 控制器和分区布局移植 NativeUfs，先以只读方式访问目标根文件系统。任何 userdata 写入都必须保持在用户确认范围内；原厂分区备份和 recovery、modem、persist 必须保留。

### 第四阶段：显示和输入

先复用 UEFI/ABL framebuffer 完成静态显示，再处理 DSI 电源和刷新。触控驱动不复用 Novatek，而是依据 Goodix Berlin 的 Linux 驱动、实时 DT 和固件文件名建立独立实现。输入初期可以使用虚拟按键验证用户空间启动链。

### 第五阶段：GPU 只读探测

先读取 GPU、GMU、SMMU 的状态和寄存器安全窗口，确认时钟、电源、固件、IOMMU stream 和中断。随后把 sheng 的 NativeAdreno 分成通用协议代码和板级常量两层，只有通用部分可以复用。Z60U 的 GPU 固件、芯片 ID、GMU 版本和 SMMU stream 必须从实机证据重新建立。

### 第六阶段：NativeAdreno 和 Metal

只有 GPU 只读探测、内存映射和 GMU 冷启动都通过后，才启用 NativeAdreno 的 ring、VM、提交、同步和 Metal 用户客户端。每一步都保持默认关闭，并使用独立启动参数，避免 GPU 失败阻塞 UFS 和显示诊断。

## 计划中的文件边界

- board.toml：最终改为 NX721J 的产品、SoC、UEFI 路径、userdata 和 ADT 参数；在实机分区布局完全核对前不写入猜测值。
- configs/nx721j_defconfig：从 sheng 配置拆出通用 XNU 选项，先关闭 sheng 专属触控、GPU、电源和频率功能。
- scripts/make-nx721j-adt.py：只使用实机 DT 证据生成 DarwinBoot/XNU 所需的 ADT，不复制 sheng 的 DT 地址。
- drivers/GoodixBerlinTouch：替代 NativeNovatekTouch，先完成协议和坐标报告，再接入 Apple HID 层。
- package/Nx721j*：存放板级电源、显示、UFS、GPU 探测和日志代码；每个硬件窗口都应有独立头文件和只读探测开关。
- uefi-z60u/Platforms/ZTE/nx721jPkg：固件平台包，不复制进本仓库的二进制子模块。

## 禁止事项

- 不把 sheng 的地址替换成 Z60U 地址后直接启动。
- 不把 DroidVM 的 VirtIO GPU 路径当成 Z60U 物理 GPU 驱动；DroidVM 的 GPU 由宿主机 KGSL 持有，和实机 NativeAdreno 不是同一条路径。
- 不在 UEFI 尚未通过前刷写 boot、vendor_boot 或 dtbo。
- 不执行 userdata 擦除、写入、GPT 修改或永久刷写，除非用户对具体破坏性步骤再次明确确认。
- 不把序列号、完整分区转储、Apple IPSW 和平台 seed 放进 Git。
